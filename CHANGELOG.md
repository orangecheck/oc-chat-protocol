# Changelog

All notable changes to the OC Chat protocol.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [0.3.5] — 2026-10-25

No envelope change. The inbox operator's drain and acknowledgement take an optional proof.

### Added
- **§8.1.5 bootstrap proofs.** A device proves its bootstrap queue with a BIP-340 signature by its inbox key over the action (`drain` or `ack`), the `bootstrap_id` and a time, and for an ack the digest of the envelope ids it acknowledges. The operator verifies it within 600 seconds and stores no key. Once a queue holding messages has been proven, a drain without a proof gets nothing from it and an acknowledgement without one is refused. An operator may drop the mark of a queue that holds no messages and has had no deposit for 30 days. A queue never proven, and every per-conversation queue, answers by its id as before. Vector **`vc21`**.

### Changed
- **§8.1.4 (2).** The operator checks the inbox pubkey of a §8.1.5 proof and MUST NOT store it.
- **§4.1.** The envelope's `from.address` counts toward the recipient's contact or UTXO policy only once its device signature verifies under a key bound to that address.
- **§8.2.5.** A record that fails the binding check MUST NOT count toward a bound a resolver applies after that check. A bound applied before it SHOULD sit far above any honest number of claimants.
- **§11** follows.

## [0.3.4] — 2026-10-24

No wire change.

### Changed
- **§8.6 host revocations.** A resolver takes the device from the signed statement and MUST NOT refuse a host revocation for its `device_id`, `device_pk` or `auth` tag. It reads the statement's named lines by name, refuses one that names a field twice, and MUST NOT refuse one for a line it does not know, so the host can add a line. The JWS still covers every line, the statement still equals the content, and `did_oc` still equals the d-tag's and `addr`.
- **§8.3.5.** A post that carries `removes` is a removal tombstone whatever its `body`. A client writes `body:""`; a reader MUST NOT refuse a removal for its body.
- **§8.3.6.** The `slug` and `channel_id` rule applies to an opted-in listing. A tombstone withdraws its founder's claim whatever its `slug`, `channel_id` or `title` say, and a resolver MUST NOT drop it for them.

## [0.3.3] — 2026-10-23

No wire change.

### Changed
- **§0, with OC Lock 2.3.0 §3.4.** From 2027-01-21T00:00:00Z by the reader's clock, a v2 device record binds no inbox key. A device re-binds as v3, which binds the same key.
- **§8.2.5** and **§8.3.1** follow: a directory listing, or a channel version without a `binding` tag, whose key only a v2 record binds stops resolving from that date until its device re-binds.

## [0.3.2] — 2026-10-22

No wire change.

### Changed
- **§8.3.1 tips at a fork.** A tip is a version that nothing on a resolving chain supersedes. Among the tips the ranking leaves, a closed tip wins, then the longest chain, then the freshest `created_at` of the signed descriptor content, then the lowest `descriptor_id`. Every reader holding the same versions picks the same tip.
- **§8.3.8.** Among the branches the §8.3.1 ranking leaves, a fork never undoes a close. The founder re-opens by superseding every closed tip.
- **§8.3.8 authority.** `successor_channel_id`, like `status`, changes only by the founder. An admin-signed supersede whose `successor_channel_id` differs from its parent's is `E_CH_UNAUTHORIZED`, whatever the status.
- **§11** follows. **`vc20`** adds the fork cases: a closed tip against a later edit and against a longer branch, a re-open against an edit, siblings with the same `created_at`, siblings whose event `created_at` runs against their signed one, a close on a branch through a revoked founder key, and two closes with one re-opened. It adds the successor cases: an admin's change to a closed channel's successor, and a successor an admin sets while the channel is active, with a close built on it and the founder's close beside it.

## [0.3.1] — 2026-10-22

No wire change.

### Changed
- **§8.6 revoked session devices.** The auth host MUST NOT vouch again for a `did_oc` and `device_id`, or a `nostr_pk`, it has revoked; a device that comes back registers a new key. A device that reads a revocation of itself MUST NOT ask for a new vouch and SHOULD stop sending. Revoking a device MUST end, in the same step, the host sign-in that obtained that device's vouch (every other sign-in of the account when the host cannot tell which one that was), and the host SHOULD offer to end the account's other sign-ins too.

## [0.3.0] — 2026-10-22

Wire change for publishers of channel descriptors. Readers keep reading channels published before it.

### Changed
- **§8.3.1 one coordinate per descriptor version.** Each version of a kind-30110 descriptor, the genesis included, is published at `d = "oc-lock-chat-ch:" || descriptor_id` with a `t` tag equal to `channel_id`, and every version but the genesis with an `s` tag equal to `supersedes`. A reader fetches every version by `#t`, paging with `until` up to a stated bound, fetches any version a `supersedes` names by its exact d-tag, and reads the legacy salted d-tag for channels published before 0.3.0. It should also read the versions each of the founder's keys signed under `#t`, and walk forward from them by `#s` with each key of the founder and the admins each version names, one key per read, revoked keys included; it walks forward only from versions those reads returned. When an open read stops at its bound, the reader reports that the channel could not be read, never that it does not exist, unless a chain resolves and those reads were complete.
- **§8.3.1 version bindings.** Every version event carries, in a `binding` tag, the kind-30078 device record that binds its key (an OC Lock v3 record, or a §8.6 session record with its vouch). A version with a later version after it on the chain is authorized by that binding; the last version also needs the binding to be live. A founder can re-sign a channel with a new genesis for the same `channel_id` when no version verifies or when the device holding `founder_inbox_pubkey` is revoked, and a client republishes the versions it signed before 0.3.0 at their own coordinate.
- **§8.3.1 fork rule.** At a fork, and among the geneses of one `channel_id`, a version the founder signed with a live binding ranks first, one the founder signed with a binding since revoked second, any other third; branches through a lower-ranked version are overruled.
- **§8.3.1 revoking a device.** A routine rotation re-signs the channels the device signed last. A device that may be in someone else's hands is never re-signed as it stands: the client shows every version it signed, republishes from a live device the confirmed versions it signed, and supersedes the confirmed version, or starts a new genesis when that device holds `founder_inbox_pubkey`.
- **§8.3.8 close.** A client MUST NOT request NIP-09 deletion of any descriptor version; the close is itself a version.
- **§8.6.** The auth host keeps every key it has signed vouches with in its JWKS, marked retired; a retired key verifies only a vouch issued before its `retired_at`, and a key that may be compromised is removed, never retired. A session device is revoked by its own key, or by the auth host with a signed `oc-chat:device-revoke:v1` statement that retires every bind of that device vouched at or before its `revoked_at` (both times the host's).
- **§10, §11, §14** follow. **`vc14`** adds the version d-tag and `t` tag; **`vc15`** gives each version its own d-tag and `s` tag.

### Added
- **`vc19`** (per-version coordinates, and reading an admin's versions under thousands of newer events, one signed with a key since revoked) and **`vc20`** (version bindings, the fork rank, and did:oc revocation by the host).

## [0.2.1] — 2026-10-22

Errata. No wire change.

### Fixed
- **§8.3.1 copies of a descriptor.** The rules did not say how a resolver treats several events that carry one `descriptor_id`. A resolver keeps every such event and accepts the descriptor if any one copy is authored as §8.3.1 requires. It counts as founder-signed at a fork if any authorized copy is the founder's, and it competes with an authorized copy's `created_at`.

## [0.1.0] — 2026-10-21

The first numbered version; the dated drafts below are 0.0. Additive and
backward compatible: a receiver that does not implement the step-up keeps
rendering session devices as `session`, which stays correct.

### Added
- **§8.6 stepping up to a Bitcoin address** — a `did:oc` session message is shown "verified · `addr`" when an OC Lock device record published by its signing key binds that key to `addr` (BIP-322 over a v3 statement, revocations applied, resolved exactly as §0). Otherwise it stays `session`. The sender is unchanged and the auth host stays the named trust anchor for the `did:oc` link; the step-up adds only the offline-verifiable link from `addr` to the key. A receiver that records each message's signing key MAY re-label earlier messages from that key.
- **`test-vectors/vc18-session-step-up.json`** — a bound key steps up; the same bind with a revocation does not.
- **§11** — a compliance line for session devices and the step-up.

## [Unreleased] — 2026-09

### Changed
- **§0 device records** — an inbox key is bound to an address as OC Lock SPEC §3.4 authorizes it: v3 device records sign the Nostr pubkey; a v2 record binds only while it is the sole pubkey carrying its `(address, device_id)`. Publishers MUST emit v3.
- **§6.3 postage** — verification now binds the invoice to the recipient's own node: the `bolt11` must be signed by a node the recipient's endpoint issues invoices from, learned from an unpaid probe invoice. `SECURITY.md` S7 names the shared-node ceiling.
- **§8.2.2 / §8.2.4 / §8.2.5 directory resolution** — replaces the conflicting "first-writer-wins" and "freshest wins, tombstone wins" rules. Binding is checked first; records are grouped by address; `created_at` orders only one address's own records; a tombstone withdraws only its author's claim; a handle held by more than one qualifying address is contested and resolves to none (`E_DIR_CONTESTED`). §8.3.6 channel handles follow the same rule.
- **§8.3.1** — a resolver ignores kind-30110 events whose `channel_id` differs from the channel being resolved.
- **§8.3.1 forks** — at a fork where the founder signed one branch, the other branches are overruled however long they grow.
- **§0 revocation** — a device revocation seen on any relay retires older binds of that device, ordered by signed timestamps.

### Added
- **§8.6 session devices** — a `did:oc` session device record is bound only by the ochk.io auth host's vouch over `(did_oc, device_pk, nostr_pk, device_id)`, obtained with a proof of possession of the Nostr key and verified against the host's JWKS.

## [Unreleased] — 2026-06

### Changed
- **`SPEC.md §8.3.8` (NORMATIVE, channel lifecycle) — founders can CLOSE/RETIRE a channel, honestly.** Comprehensive research (Nostr NIP-09/NIP-01/NIP-62 deletion semantics, the family content-addressed/offline-verifiable invariants, and how Telegram/Discord/Matrix/NIP-29 handle it) concluded that a *true delete* is impossible and would overclaim: a channel is a content-addressed kind-30110 descriptor + signed public kind-30111 posts on relays OC doesn't control. So "delete" is specified as **close/retire forward, never erase**: a founder-signed supersede flips a new optional `status:"closed"` field (OMITTED when active ⇒ vc14/vc15 byte-unaffected); a closed channel renders read-only and denies new posts with new error `E_CH_CLOSED` while STILL accepting removal tombstones (moderation survives close); the `status` transition is **founder-only** (an admin-signed close/reopen is `E_CH_UNAUTHORIZED` — the §8.3.1 coup guard); reversible via a later `status:"active"`. On close a client SHOULD also fire the §8.3.6 kind-30114 directory tombstone + a best-effort NIP-09 (never shown as success). New `SECURITY.md` S-CH-8 names the honest ceiling (cannot erase the descriptor/posts, retract scraped copies, force a relay to forget, or reclaim `channel_id`); NIP-62 vanish noted as a stronger future option. Reference client (`chat.ochk.io`): founder-only Danger "Close channel" (never "Delete") with a typed-title confirm + verbatim honest copy + read-only closed banner + re-open; verifyDescriptor founder-only status rule + checkWritePolicy `E_CH_CLOSED` (tombstones exempt); 6 new tests incl. admin-close-denied. `optedIn:false` directory tombstone reused for the un-list.
- **`SPEC.md §8.3.6` (NORMATIVE, anti-squat fix)** — a channel directory listing (kind-30114) MUST now carry `slug`, and its `channel_id` MUST equal the §8.3.1 derivation `SHA-256("oc-lock-chat-ch/v1:" || founder_address || ":" || lower(slug))`; a resolver MUST recompute and **drop any listing whose `channel_id` is not so derived**. The prior wording let the listing carry `channel_id` as a **free field** validated only by the §8.2.2 founder gates (inbox↔address binding + UTXO floor) — which prove the *lister* is Bitcoin-real but say **nothing** about authority over the channel the handle points at. So anyone with one funded+aged address + a bound inbox key could publish `@bitcoin → a victim's channel they never founded` (a handle-hijack). Binding `channel_id` to `(founder_address ‖ slug)` makes the mapping self-proving: because the listing is signed by an inbox key device-bound to `founder_address`, a derivable `channel_id` can only ever point at a channel *this* founder rooted. Offline-self-proving (no second descriptor fetch). Reference client (`chat.ochk.io`): enforced at both ends — `buildChannelListingEvent` throws `E_CH_DIRECTORY_SLUG_MISMATCH` on a non-derived id, `resolveChannelHandle` drops any (even validly-signed, hand-forged) listing whose id is not derived; new build-guard + forged-listing-dropped tests.
- **`SPEC.md §8.3.3` (NORMATIVE, Bitcoin-load-bearing fix)** — the `utxo-floor` write-proof MUST now be verified against **public chain data**, not accepted as a self-contained claim. The prior wording ("self-contained, no per-post live point-query") left `value_sats` + `anchor_block_height` as **author-asserted numbers a `control_sig` over ANY unfunded address would clear** — a forger could claim a huge value + old height and post to a Bitcoin-gated channel with no qualifying coin, defeating invariant 1 (Bitcoin load-bearing). A conforming reader now confirms the proof's `outpoint` is an **UNSPENT output OWNED BY** the UTXO address (it appears in that address's UTXO set) carrying the **exact** `value_sats`/`anchor_block_height`/`anchor_block_hash` claimed, **before** the floor arithmetic + `control_sig`. The original DoS/fail-open concern is met by **deduping the query per-outpoint (one address-UTXO fetch per distinct author per render batch, not per post) and FAILING CLOSED** (an unverifiable proof drops the post; never renders unverified). Reference client (`chat.ochk.io`): `verifyWriteProofOnChain` wired into the channel-post verify path with that per-batch dedup; forged-value / not-owned-outpoint / forged-height / fail-closed all covered by new tests. (`vc17` is unaffected — it tests the floor arithmetic, which still runs after the chain bind.)
- **`SECURITY.md` S1 + threat model** — disclosed the at-rest device-key storage posture (the reference client now AES-GCM-wraps `device_sk` under a **non-extractable** WebCrypto key). S1 names the honest boundary per W3C WebCrypto L2 §6.2: the wrap raises the bar against in-page (XSS) key-exfiltration **only** — the wrap key rests beside the ciphertext, so it does **not** protect a seized/disk-imaged/backed-up device (that relies on OS full-disk encryption); message plaintext also rests unencrypted locally. The only at-rest defense that survives seizure is an opt-in passphrase app-lock (PBKDF2), which is deferred. The threat model's "runtime not compromised" assumption is scoped to **while running** and explicitly does NOT assume a cold-seized/imaged/backed-up device is safe (that case is in scope, addressed in S1).
- **`SPEC.md §4.1/§4.2/§6.3` + `PROTOCOL.md` Flow 3** — clarified the free-tier/postage hold as a presentation-neutral **filtered/pending** state (the "Requests" surface), not a separate "Requests tray" page. The normative routing is unchanged (a below-floor or invalid-postage first-contact is **delivered, decrypted, and shown to the recipient set apart from the main inbox — never dropped**). Specified acceptance as a **client-local, explicit, revocable allowlist** (the recipient approving a sender — e.g. by opening their filtered conversation — lets them reach the inbox normally thereafter; revocable anytime) that MUST NOT be published, carried on the wire, or co-indexed with the directory (the §8.2.3 social-graph firewall). A recipient signals acceptance to a sender only by replying; clients MUST NOT emit a separate "your request was opened" receipt (a read-receipt-style metadata leak — SECURITY S19). Reference client (`chat.ochk.io`): the standalone Requests page was removed in favor of an inline, distinct Requests group.

- **`SPEC.md §6`** — pay-to-reach postage specified (was a blocking open item). The recipient publishes an **identity-signed** Lightning Address; the sender's fresh per-DM **nonce** (LUD-18 payerData) makes the recipient's own endpoint mint a BOLT11 whose **description-hash commits recipient + amount + nonce**, which the recipient **re-derives itself** (wallets dropped it, lnurl #234) over verbatim bytes. Bitcoin-load-bearing: the preimage is a settled-HTLC bearer proof (no Ed25519 analog).

A file rides as an `attachment` field INSIDE the AES-256-GCM-sealed ChatBody (the inline v0 profile), so no server ever holds a plaintext file and altering it breaks the content-addressed id + device signature. Size-bounded to a gift-wrap event (~100KB raw in the reference client); the blob-store upgrade (per-file key in the ciphertext, ciphertext blob uploaded out-of-band) lifts the cap without breaking the no-plaintext-on-a-server invariant.
- **`SPEC.md §7.6`** — seal-til-block v0 profile specified + SHIPPED (`chat.ochk.io`). The shipped `@orangecheck/lock-core@1.0.1` has no `chat-seal` kind and no committed top-level `seal` field, so v0 carries the seal **inside the encrypted ChatBody** (the postage precedent): the body text is AES-256-GCM-locked under a reveal secret `R`, and `R` is **drand-quicknet timelock-encrypted** to a round derived from the target block (`tlock`). drand IS the beacon (League of Entropy, ~12-of-22 BLS — not OC, not Bitcoin); there is **no OC re-wrap endpoint**. **Hard chain gate (normative):** a conforming recipient MUST NOT surface the body until it independently confirms `chain_tip ≥ unlock_block + confirmations` against a named explorer, EVEN IF `tlock` already yielded `R` — so a message opens at the **later** of (drand round, real block height). The release leg FAILS the Ed25519 test (drand is Bitcoin-independent; said out loud on every surface); the `unlock_block` is a recipient-verified condition, not the key holder. v0 caps the horizon at ~30 days; "trustless" is banned; the spec-pure beacon-device re-wrap path (§7.1–7.3, vectors `vc03`/`vc04`) is the named upgrade target needing a lock-core bump. New vectors `vc10` (round derivation), `vc11` (AES body round-trip), `vc12` (live drand tlock decrypt), `vc13` (id-stability / tamper-evidence).
- **`SPEC.md §8.3`** — **Channels (v1: public)** made normative. A channel is a composition: a kind-30110 governance **descriptor** (founder-address-rooted, BIP-322-signed, a governance hash-chain via `supersedes` validated against the prior epoch's admins) + kind-30111 **posts** (the new `chat-channel` EnvelopeKind — §3 amended; public, plaintext, recipient-less, content-addressed, BIP-322-signed) + (opt-in) a kind-30114 directory listing + a Bitcoin-priced **write gate**. The descriptor's `read` + `encryption` fields are the phase switch: v1 public; private channels (`read:"members"` + an `encryption` block + kind-30113 group-key epochs) are reserved behind the SAME descriptor (§8.3.7). Write policies: `utxo-floor` (canonical default, `rooted:true` — a self-contained **height-anchored** UTXO write-proof, verified OFFLINE with no per-post live point-query; passes the Ed25519 substitution test), `allowlist`/`founder`/`open` (`rooted:false` — NOT Bitcoin-load-bearing, rendered "via ochk.io" muted tier); `pay-to-post` deferred to the kind-30115 registry extension (needs an invoice round-trip, not offline-verifiable). The `write.rooted` flag MUST match the policy (`E_CH_POLICY_INVALID`), making the Bitcoin claim a property of the artifact, not a UI label. Five roles (founder/admin/moderator/writer/reader) enforced offline by signature; forward-effective tombstone moderation; directory composition under the §8.2 rules. The S9 social-graph leak that deferred groups **evaporates** for public channels — a public post has no `recipients[]`, so there is nothing to leak (`E_CHANNEL_RECIPIENTS` on a non-empty one). New error codes `E_CHANNEL_RECIPIENTS`/`E_CH_POLICY_INVALID`/`E_CH_UNAUTHORIZED`/`E_CH_WRITE_DENIED`/`E_CH_NOT_WRITER`/`E_CHAN_FLOOR`; SECURITY S-CH-1..7 (incl. S-CH-3, the on-chain UTXO ownership-map leak the default policy creates — a STRONGER deanonymization than DMs); kinds 30110/30111 reserved → allocated, 30113/30115 reserved; compliance-checklist + IANA roll-up; vectors `vc14` (descriptor id + d-tag + policy-rooted match), `vc15` (governance supersession), `vc16` (public post id + recipient-exclusion), `vc17` (height-anchored UTXO write-proof arithmetic). All four reproduce. Canonical design: `research/CHANNELS-PLAN.md`. NOT a 7th verb — a composition; OC Chat stays a mode of OC Lock. Web build (lib + UI) follows; v1 ships public only.
- **`SPEC.md §8`** — wrap encryption made normative + SHIPPED (`ct = "oc-chat/v2"`). The v1 wrap content was plaintext base64: any relay (and the §8.1 inbox operator) could decode the embedded envelope and read `from.address`, every `recipients[*].address`, the device set, full-precision timestamps, and the sender's stable device pubkey — the full who-talks-to-whom graph, voiding §8.1.4's operator-blindness. v2 encrypts the wrap content to the recipient inbox key: ECDH(ephemeral signer key × inbox pubkey, x-coordinate only — negation-safe for BIP-340 x-only keys) → HKDF-SHA256 bound to the `(eph_pk, inbox_pk)` pair → AES-256-GCM, `content = base64url(nonce || ct)`. Publishers MUST emit v2; v1 is accepted on receive only. The inbox `p` tag + timing remain the disclosed §8.1.2 leak.
- **`SPEC.md §8.1`** — durable-inbox routing made normative: opaque per-conversation `queue_id = base64url(HMAC-SHA256(HKDF-SHA256(device_sk), conversation_id))`, a derivable first-contact `bootstrap_id`, the in-payload `recv_queue` handshake (§5), and four operator obligations (ciphertext-only, route-on-opaque-id, hold-no-keys, availability-not-authority). Closes the S6/S10 gap where the inbox routing key was named but unspecified — without it a store-and-forward operator could link a recipient's conversations. Free-tier floor; the paid tier extends only retention/multi-device/history.
