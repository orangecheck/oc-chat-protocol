# Changelog

All notable changes to the OC Chat protocol.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased] — 2026-06

### Changed
- **`SPEC.md §8.3.8` (NORMATIVE, channel lifecycle) — founders can CLOSE/RETIRE a channel, honestly.** Comprehensive research (Nostr NIP-09/NIP-01/NIP-62 deletion semantics, the family content-addressed/offline-verifiable invariants, and how Telegram/Discord/Matrix/NIP-29 handle it) concluded that a *true delete* is impossible and would overclaim: a channel is a content-addressed kind-30110 descriptor + signed public kind-30111 posts on relays OC doesn't control. So "delete" is specified as **close/retire forward, never erase**: a founder-signed supersede flips a new optional `status:"closed"` field (OMITTED when active ⇒ vc14/vc15 byte-unaffected); a closed channel renders read-only and denies new posts with new error `E_CH_CLOSED` while STILL accepting removal tombstones (moderation survives close); the `status` transition is **founder-only** (an admin-signed close/reopen is `E_CH_UNAUTHORIZED` — the §8.3.1 coup guard); reversible via a later `status:"active"`. On close a client SHOULD also fire the §8.3.6 kind-30114 directory tombstone + a best-effort NIP-09 (never shown as success). New `SECURITY.md` S-CH-8 names the honest ceiling (cannot erase the descriptor/posts, retract scraped copies, force a relay to forget, or reclaim `channel_id`); NIP-62 vanish noted as a stronger future option. Reference client (`chat.ochk.io`): founder-only Danger "Close channel" (never "Delete") with a typed-title confirm + verbatim honest copy + read-only closed banner + re-open; verifyDescriptor founder-only status rule + checkWritePolicy `E_CH_CLOSED` (tombstones exempt); 6 new tests incl. admin-close-denied. `optedIn:false` directory tombstone reused for the un-list.
- **`SPEC.md §8.3.6` (NORMATIVE, anti-squat fix)** — a channel directory listing (kind-30114) MUST now carry `slug`, and its `channel_id` MUST equal the §8.3.1 derivation `SHA-256("oc-lock-chat-ch/v1:" || founder_address || ":" || lower(slug))`; a resolver MUST recompute and **drop any listing whose `channel_id` is not so derived**. The prior wording let the listing carry `channel_id` as a **free field** validated only by the §8.2.2 founder gates (inbox↔address binding + UTXO floor) — which prove the *lister* is Bitcoin-real but say **nothing** about authority over the channel the handle points at. So anyone with one funded+aged address + a bound inbox key could publish `@bitcoin → a victim's channel they never founded` (a handle-hijack). Binding `channel_id` to `(founder_address ‖ slug)` makes the mapping self-proving: because the listing is signed by an inbox key device-bound to `founder_address`, a derivable `channel_id` can only ever point at a channel *this* founder rooted. Offline-self-proving (no second descriptor fetch). Reference client (`chat.ochk.io`): enforced at both ends — `buildChannelListingEvent` throws `E_CH_DIRECTORY_SLUG_MISMATCH` on a non-derived id, `resolveChannelHandle` drops any (even validly-signed, hand-forged) listing whose id is not derived; new build-guard + forged-listing-dropped tests.
- **`SPEC.md §8.3.3` (NORMATIVE, Bitcoin-load-bearing fix)** — the `utxo-floor` write-proof MUST now be verified against **public chain data**, not accepted as a self-contained claim. The prior wording ("self-contained, no per-post live point-query") left `value_sats` + `anchor_block_height` as **author-asserted numbers a `control_sig` over ANY unfunded address would clear** — a forger could claim a huge value + old height and post to a Bitcoin-gated channel with no qualifying coin, defeating invariant 1 (Bitcoin load-bearing). A conforming reader now confirms the proof's `outpoint` is an **UNSPENT output OWNED BY** the UTXO address (it appears in that address's UTXO set) carrying the **exact** `value_sats`/`anchor_block_height`/`anchor_block_hash` claimed, **before** the floor arithmetic + `control_sig`. The original DoS/fail-open concern is met by **deduping the query per-outpoint (one address-UTXO fetch per distinct author per render batch, not per post) and FAILING CLOSED** (an unverifiable proof drops the post; never renders unverified). Reference client (`chat.ochk.io`): `verifyWriteProofOnChain` wired into the channel-post verify path with that per-batch dedup; forged-value / not-owned-outpoint / forged-height / fail-closed all covered by new tests. (`vc17` is unaffected — it tests the floor arithmetic, which still runs after the chain bind.)
- **`SECURITY.md` S1 + threat model** — disclosed the at-rest device-key storage posture (the reference client now AES-GCM-wraps `device_sk` under a **non-extractable** WebCrypto key). S1 names the honest boundary per W3C WebCrypto L2 §6.2: the wrap raises the bar against in-page (XSS) key-exfiltration **only** — the wrap key rests beside the ciphertext, so it does **not** protect a seized/disk-imaged/backed-up device (that relies on OS full-disk encryption); message plaintext also rests unencrypted locally. The only at-rest defense that survives seizure is an opt-in passphrase app-lock (PBKDF2), which is deferred. The threat model's "runtime not compromised" assumption is scoped to **while running** and explicitly does NOT assume a cold-seized/imaged/backed-up device is safe (that case is in scope, addressed in S1).
- **`SPEC.md §4.1/§4.2/§6.3` + `PROTOCOL.md` Flow 3** — clarified the free-tier/postage hold as a presentation-neutral **filtered/pending** state (the "Requests" surface), not a separate "Requests tray" page. The normative routing is unchanged (a below-floor or invalid-postage first-contact is **delivered, decrypted, and shown to the recipient set apart from the main inbox — never dropped**). Specified acceptance as a **client-local, explicit, revocable allowlist** (the recipient approving a sender — e.g. by opening their filtered conversation — lets them reach the inbox normally thereafter; revocable anytime) that MUST NOT be published, carried on the wire, or co-indexed with the directory (the §8.2.3 social-graph firewall). A recipient signals acceptance to a sender only by replying; clients MUST NOT emit a separate "your request was opened" receipt (a read-receipt-style metadata leak — SECURITY S19). Reference client (`chat.ochk.io`): the standalone Requests page was removed in favor of an inline, distinct Requests group.

### Added
- Initial OC Chat protocol specification. OC Chat is a **mode of OC Lock**, not a new verb: it adds two envelope `kind` values (`chat`, `chat-seal`) to the OC Lock v2 envelope and a thin threading/postage/seal layer on top of the unchanged X25519 + AES-256-GCM crypto.
- **`SPEC.md`** — normative: the recipient-exclusion `id`/AAD rule for chat kinds (§3), the three canonical send modes `speak-now` / `pay-to-reach` / `seal-til-block` (§4), encrypted threading with a hash-chain `parent_id` (§5), postage preimage-binding and replay defense (§6), the seal beacon release protocol (§7), error codes (§9), and the Nostr kind allocation 30110–30112 with the `oc-lock-chat-*` d-tag namespace (§10).
- **`PROTOCOL.md`** — narrative walkthrough: five flows (speak-now, multi-device, pay-to-reach, seal-til-block + release, standing-delivery).
- **`SECURITY.md`** — threat model + ≥10 attack scenarios, including the SEAL's beacon-trust posture, the OR-double-seal early-release asymmetry, and the seal-metadata leak.
- **`WHY.md`** — hypothesis-by-hypothesis rationale, including the Ed25519 substitution test run out loud on the seal.
- **`test-vectors/`** — six reproducible fixtures, including `vc04` proving re-wrap `id`/tag stability and `vc06` proving per-conversation queue-id unlinkability.
- **`SPEC.md §6`** — pay-to-reach postage specified (was a blocking open item). The recipient publishes an **identity-signed** Lightning Address; the sender's fresh per-DM **nonce** (LUD-18 payerData) makes the recipient's own endpoint mint a BOLT11 whose **description-hash commits recipient + amount + nonce**, which the recipient **re-derives itself** (wallets dropped it, lnurl #234) over verbatim bytes. Postage rides in the **encrypted ChatBody** (v0; lock-core `seal()` can't commit it as an envelope field), carrying `bolt11`/`lnurl_metadata`/`payerdata` for offline re-verification. Replay defense = the binding (cross-recipient) + a **local spent-`payment_hash` ledger** (same-recipient). S7 promoted to "specified, recipient-scoped — **not** third-party-transferable", with the named ceiling (the endpoint is a trust anchor; bearer-proof not on-chain-settlement-proof). vc05 reconciled to body-carried; new vector `vc09` (preimage→payment_hash, the LUD-18 binding, the replay branch). Bitcoin-load-bearing: the preimage is a settled-HTLC bearer proof (no Ed25519 analog).
- **`SPEC.md §8.2`** — opt-in discoverability directory (kind **30114**, d-tag `oc-lock-chat-dir:<salted handle hash>`): a NIP-33-replaceable listing signed by the inbox key, found by a human-readable handle. **Default invisible.** The Bitcoin gate (§8.2.2) is load-bearing — a resolver honors a handle only if the inbox key is bound to the address via the kind-30078 device record AND the address clears a funded+aged UTXO floor (no Ed25519 analog → Sybil/anti-squat); a bare signed-presence listing fails the substitution test. Social-graph firewall (§8.2.3): reveals a node, never an edge. Tombstone revocation (§8.2.4), forward-effective only. New error codes `E_DIR_UNVERIFIED`/`E_DIR_REVOKED`; SECURITY S14–S17 (scrapeable oracle, forward-only revocation, intentional deanonymization, non-authoritative handles); vectors `vc07` (d-tag) + `vc08` (listing id + tombstone). NOT OC Find — OC Find is an unbuilt research idea; its reserved 30094–30109 block is left untouched.
- **`SPEC.md §5.1`** — E2EE attachments specified + SHIPPED (`chat.ochk.io`). A file rides as an `attachment` field INSIDE the AES-256-GCM-sealed ChatBody (the inline v0 profile), so no server ever holds a plaintext file and altering it breaks the content-addressed id + device signature. Size-bounded to a gift-wrap event (~100KB raw in the reference client); the blob-store upgrade (per-file key in the ciphertext, ciphertext blob uploaded out-of-band) lifts the cap without breaking the no-plaintext-on-a-server invariant.
- **`SPEC.md §7.6`** — seal-til-block v0 profile specified + SHIPPED (`chat.ochk.io`). The shipped `@orangecheck/lock-core@1.0.1` has no `chat-seal` kind and no committed top-level `seal` field, so v0 carries the seal **inside the encrypted ChatBody** (the postage precedent): the body text is AES-256-GCM-locked under a reveal secret `R`, and `R` is **drand-quicknet timelock-encrypted** to a round derived from the target block (`tlock`). drand IS the beacon (League of Entropy, ~12-of-22 BLS — not OC, not Bitcoin); there is **no OC re-wrap endpoint**. **Hard chain gate (normative):** a conforming recipient MUST NOT surface the body until it independently confirms `chain_tip ≥ unlock_block + confirmations` against a named explorer, EVEN IF `tlock` already yielded `R` — so a message opens at the **later** of (drand round, real block height). The release leg FAILS the Ed25519 test (drand is Bitcoin-independent; said out loud on every surface); the `unlock_block` is a recipient-verified condition, not the key holder. v0 caps the horizon at ~30 days; "trustless" is banned; the spec-pure beacon-device re-wrap path (§7.1–7.3, vectors `vc03`/`vc04`) is the named upgrade target needing a lock-core bump. New vectors `vc10` (round derivation), `vc11` (AES body round-trip), `vc12` (live drand tlock decrypt), `vc13` (id-stability / tamper-evidence).
- **`SPEC.md §8.3`** — **Channels (v1: public)** made normative. A channel is a composition: a kind-30110 governance **descriptor** (founder-address-rooted, BIP-322-signed, a governance hash-chain via `supersedes` validated against the prior epoch's admins) + kind-30111 **posts** (the new `chat-channel` EnvelopeKind — §3 amended; public, plaintext, recipient-less, content-addressed, BIP-322-signed) + (opt-in) a kind-30114 directory listing + a Bitcoin-priced **write gate**. The descriptor's `read` + `encryption` fields are the phase switch: v1 public; private channels (`read:"members"` + an `encryption` block + kind-30113 group-key epochs) are reserved behind the SAME descriptor (§8.3.7). Write policies: `utxo-floor` (canonical default, `rooted:true` — a self-contained **height-anchored** UTXO write-proof, verified OFFLINE with no per-post live point-query; passes the Ed25519 substitution test), `allowlist`/`founder`/`open` (`rooted:false` — NOT Bitcoin-load-bearing, rendered "via ochk.io" muted tier); `pay-to-post` deferred to the kind-30115 registry extension (needs an invoice round-trip, not offline-verifiable). The `write.rooted` flag MUST match the policy (`E_CH_POLICY_INVALID`), making the Bitcoin claim a property of the artifact, not a UI label. Five roles (founder/admin/moderator/writer/reader) enforced offline by signature; forward-effective tombstone moderation; directory composition under the §8.2 rules. The S9 social-graph leak that deferred groups **evaporates** for public channels — a public post has no `recipients[]`, so there is nothing to leak (`E_CHANNEL_RECIPIENTS` on a non-empty one). New error codes `E_CHANNEL_RECIPIENTS`/`E_CH_POLICY_INVALID`/`E_CH_UNAUTHORIZED`/`E_CH_WRITE_DENIED`/`E_CH_NOT_WRITER`/`E_CHAN_FLOOR`; SECURITY S-CH-1..7 (incl. S-CH-3, the on-chain UTXO ownership-map leak the default policy creates — a STRONGER deanonymization than DMs); kinds 30110/30111 reserved → allocated, 30113/30115 reserved; compliance-checklist + IANA roll-up; vectors `vc14` (descriptor id + d-tag + policy-rooted match), `vc15` (governance supersession), `vc16` (public post id + recipient-exclusion), `vc17` (height-anchored UTXO write-proof arithmetic). All four reproduce. Canonical design: `research/CHANNELS-PLAN.md`. NOT a 7th verb — a composition; OC Chat stays a mode of OC Lock. Web build (lib + UI) follows; v1 ships public only.
- **`SPEC.md §8`** — wrap encryption made normative + SHIPPED (`ct = "oc-chat/v2"`). The v1 wrap content was plaintext base64: any relay (and the §8.1 inbox operator) could decode the embedded envelope and read `from.address`, every `recipients[*].address`, the device set, full-precision timestamps, and the sender's stable device pubkey — the full who-talks-to-whom graph, voiding §8.1.4's operator-blindness. v2 encrypts the wrap content to the recipient inbox key: ECDH(ephemeral signer key × inbox pubkey, x-coordinate only — negation-safe for BIP-340 x-only keys) → HKDF-SHA256 bound to the `(eph_pk, inbox_pk)` pair → AES-256-GCM, `content = base64url(nonce || ct)`. Publishers MUST emit v2; v1 is accepted on receive only. The inbox `p` tag + timing remain the disclosed §8.1.2 leak.
- **`SPEC.md §8.1`** — durable-inbox routing made normative: opaque per-conversation `queue_id = base64url(HMAC-SHA256(HKDF-SHA256(device_sk), conversation_id))`, a derivable first-contact `bootstrap_id`, the in-payload `recv_queue` handshake (§5), and four operator obligations (ciphertext-only, route-on-opaque-id, hold-no-keys, availability-not-authority). Closes the S6/S10 gap where the inbox routing key was named but unspecified — without it a store-and-forward operator could link a recipient's conversations. Free-tier floor; the paid tier extends only retention/multi-device/history.
- **`SPEC.md §8.4 / §8.5 / §6.5` (M7 institutional — spec-first)** — three institutional-tier mechanisms specified (web build follows; canonical plan `research/INSTITUTIONAL-PLAN.md`). **§8.4 Relay AUTH (NIP-42):** an `auth-required` relay gates the connection so an unauthenticated observer never sees the recipient `p` tag (closes the S6 metadata leak for self-hosted/institutional relays). The kind-22242 handshake is signed by a **fresh per-connection ephemeral key** (default — pure access-gating, links to no identity or message) or a designated `auth_key` when a relay allow-lists members; `E_RELAY_AUTH_REQUIRED`. Honest: AUTH is **not** Bitcoin-load-bearing (works with any keypair) — a metadata hardening that rides on the §3 identity, not a new claim. **§8.5 Source-intake mode:** a SecureDrop-shaped composition of shipped primitives (public `write:"open"` intake channel in + gift-wrapped private reply out to the source's inbox key) — **no new kind, no new crypto**; the source uses an ephemeral identity, the org stays Bitcoin-rooted, the §8.2.3 firewall reveals the drop, never the source set. **§6.5 Named-Fedimint custodial fallback:** a recipient with no Lightning endpoint names a **federation** as their postage last-mile (published in their own §6.1 listing; §6.3 verification unchanged) — the **federation** custodies + settles ecash, OC touches no sats / runs no guardian share / holds no hot wallet (the family "federations settle, OC never pays" corollary). The federation is a named plaintext trust anchor; `E_FEDIMINT_UNAVAILABLE` / `E_FEDIMINT_BINDING_MISMATCH`. **Deployment gate (normative):** the Fedimint postage path ships only after a money-transmitter analysis (WHY §19 #5) clears — the federation custodies inbound funds. Lightning settlement remains the Bitcoin-load-bearing hook. kind-22242 noted in §10 as a NIP-42 protocol (not OC-allocated) kind. No new test vectors: none of the three introduces a new content-addressed artifact (AUTH is an ephemeral handshake; source-intake reuses existing kinds; Fedimint reuses the §6.3 binding). Completed across the spec set: **`PROTOCOL.md` Flow 6** (institutional / source-intake walkthrough) + **`SECURITY.md` S-M7-1..3** (AUTH relay is a named trust anchor + not Bitcoin-load-bearing; source-intake submissions are permanently public, only the reply is private; the Fedimint fallback shifts custody to the federation's guardian threshold).

### Honesty notes (normative posture, not marketing)
- The `seal-til-block` unlock is **beacon-enforced policy, not consensus**. The v0 beacon is **drand quicknet tlock** (named, not OC-controlled). The word "trustless" MUST NOT appear on any v0 seal surface. A Bitcoin-consensus-enforced seal (CLTV-witness) is a structurally pre-wired upgrade path (`seal.cltv_outpoint`), not shipped.
- OC operates **no payment rail** for postage. Sender and recipient transact directly; OC verifies the preimage offline and never custodies sats.
